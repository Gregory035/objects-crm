# Объекты и задачи
Мини-CRM строительной команды: React + TypeScript + Supabase.

## Запуск
Node.js 22+. Выполните `npm ci`, скопируйте `.env.example` в `.env.local` и задайте URL Supabase и publishable key. `npm run dev` запускает приложение, `npm run build` проверяет TypeScript и собирает production-версию.

## База
SQL в `supabase/migrations` применяется по порядку к новому проекту Supabase. Отключите Allow new users to sign up в Authentication → Sign In / Providers. Создайте пользователей через Authentication → Users, затем добавьте строки в `public.profiles` с соответствующими UUID, именами и ролями `manager`/`worker`. Секретные ключи во фронтенд не передаются. Роли хранятся в защищённой таблице; пользователь не может менять свою роль.

## Безопасность
RLS ограничивает чтение и запись. Исполнитель видит только свои задачи и связанные объекты. Триггер проверяет разрешённые переходы и неизменность остальных полей, создаёт историю в той же транзакции. Прямые INSERT/UPDATE/DELETE истории и изменение профилей для клиентов запрещены. Автор и дата создания назначаются сервером. Внутренние функции находятся в закрытой схеме, имеют фиксированный search_path и ограниченные права выполнения.

## Решения и допущения
- Постановщики видят все объекты и задачи общей команды.
- Удаление мягкое: записи скрываются из рабочих списков, история физически сохраняется. Восстановление доступно администратору базы, интерфейс восстановления не входит в задание.
- Объект можно удалить только после удаления его задач; правило проверяется базой.
- Смена исполнителя и объекта не сбрасывает статус. Изменение данных и статуса выполняется отдельными операциями.
- Принятая задача не возвращается в работу: такой переход отсутствует в ТЗ.
- История включает создание задачи. Комментарий необязателен при приёмке и обязателен при возврате.
- Пользователи создаются администратором Supabase; управления сотрудниками и открытой регистрации в приложении нет.
- Обновление данных — при действиях пользователя и кнопкой «Обновить», без realtime.
- Данные демонстрационные; названия и адреса условные.

## Объяснение руководителю
В системе есть руководители и исполнители. Руководитель создаёт стройку, добавляет задачи и назначает ответственных. Исполнитель видит только назначенные ему задачи и связанные стройки. Он берёт задачу в работу и передаёт результат на проверку. Руководитель принимает работу или возвращает её с обязательным пояснением.

Каждое изменение статуса автоматически попадает в историю: видно, кто и когда выполнил действие. Исполнитель не может назначить себя на чужую задачу, изменить её содержание или самостоятельно принять работу. Эти ограничения проверяет сама база данных, поэтому их нельзя обойти изменением страницы или отправкой запроса вручную. Историю нельзя отредактировать через приложение или его API. Самостоятельная регистрация отключена; доступ выдаёт администратор.

## Размещение
GitHub Pages, автоматическая сборка через GitHub Actions. Используется hash-навигация, поэтому ссылки на карточки работают без серверного маршрутизатора. Publishable key намеренно доступен браузеру: безопасность обеспечивают права базы, а не сокрытие этого ключа.
